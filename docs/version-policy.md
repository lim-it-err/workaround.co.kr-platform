문서 상태: 작성완료

# 버전 정책

## 목적

워커와 오케스트레이터가 현재 릴리스, 다음 개발 목표, 인프라/문서 작업 범위를 혼동하지 않도록 버전 기준을 분리한다.

## 기준 파일

- `VERSION`: 최신 배포 완료 버전만 적는다.
- `docs/releases.md`: 릴리스 기록과 현재 개발 상한을 적는다.
- `docs/tickets/board.md`: 지금 실제로 집을 수 있는 작업 목록을 적는다.
- 각 티켓 파일: 해당 작업의 `target version` 을 적는다.

## 현재 버전 확인 방법

작업자는 아래 순서로 현재 버전과 작업 가능 범위를 확인한다.

1. `VERSION` 파일을 읽어 최신 배포 완료 버전을 확인한다.
2. `docs/releases.md` 의 `현재 릴리스 상태` 와 `현재 개발 상한` 을 확인한다.
3. `docs/tickets/board.md` 에서 실제로 열려 있는 티켓을 확인한다.
4. 작업할 티켓의 `대상 버전`, `선행 조건`, `질문/결정 기록` 을 확인한다.
5. 작업할 티켓의 `진행 판정` 을 확인한다.

`VERSION` 값이 `0.1.0` 이라면 이는 최신 배포 완료 버전이 `v0.1.0` 이라는 뜻이다. 이것만으로 다음 작업 범위가 자동 결정되지는 않는다.

## 핵심 규칙

- 워커는 `VERSION` 만 보고 다음 버전을 추론하지 않는다.
- 워커는 항상 티켓의 `target version` 과 `docs/releases.md` 의 현재 개발 상한을 함께 본다.
- 현재 단계에서는 "하나의 release version = 하나의 기능 테마" 원칙을 둔다. 여러 티켓이 있더라도 같은 버전 안에서는 하나의 기능 묶음만 다룬다.
- 작업자는 최신 배포 완료 버전의 다음 minor까지는 자유롭게 티켓을 선택할 수 있다.
- 단, 자유롭게 선택할 수 있다는 말은 `docs/tickets/board.md` 에 열려 있고 선행 조건을 만족한 티켓 안에서만 의미한다.
- 현재 `VERSION` 이 `0.1.0` 이므로, 버전 기능 작업은 기본적으로 `v0.2.x` 범위까지 본다.
- 하지만 개별 티켓의 `진행 판정` 이 `진행 불가` 이거나 `vX.Y.Z 진행 시 가능` 이면, worker는 해당 판정이 풀리기 전까지 시작하지 않는다.
- 사용자가 "v0.2.0 배포해도 돼" 라고 명시하고 `main` 병합이 끝난 뒤에만 `VERSION` 을 `0.2.0` 으로 올린다.
- `v0.2.0` 릴리스 완료 후 오케스트레이터가 다음 개발 상한을 정리하기 전까지 워커는 임의로 `v0.3.0` 작업을 만들지 않는다.
- 단, 사용자가 `localhost` 확인 후 `v0.3.0`, 이어서 `v0.4.0`, `v0.5.0` 이하 작업도 진행하라고 명시하면 오케스트레이터는 해당 티켓을 시작 가능 상태로 열 수 있다.
- 이 예외가 열려 있어도 `v0.3.0`, `v0.4.0`, `v0.5.0` 은 선작업일 뿐이며, `v0.2.0` 배포 완료나 `VERSION=0.2.0` 을 뜻하지 않는다.
- 이 경우에도 `VERSION` 승격, `v0.2.0` 릴리스 태그, `v0.3.0`/`v0.4.0`/`v0.5.0` 릴리스 기준선 생성은 사용자의 별도 승인 전까지 하지 않는다.
- 현재 로드맵 기준으로 `v0.2.0` 이후 다음 minor 후보는 `v0.3.0` 이며, 엘리베이터 시뮬레이터는 이 후보에 둔다.
- `v0.3.0` 이후 다음 minor 후보로는 `v0.4.0` 을 둘 수 있으며, 이 후보에는 Work Manager 운영 트랙을 둔다.
- `v0.4.0` 준비 작업은 보드 UI, `Backlog/Ready` 분리와 상세 패널, 티켓 이동/실행 브리지, command 비밀번호 게이트, 메타데이터 편집, Main page 라우팅, 다크모드, 테스트/CI/커버리지, PR 버전 가드를 분리해서 적는다.
- `v0.5.0` 은 `v0.4.0` 뒤의 다음 시뮬레이션 minor 로 두고, 택시 시뮬레이터 포털과 코어를 둔다.
- `v0.5.1` 은 `v0.5.0` 뒤의 후속 슬라이스로 두고, 사람 피드백 반영과 자동 학습 루프 같은 운영 기능을 넣는다.
- `v0.6.0` 은 블로그 공간, 글쓰기 스튜디오, 공개 아카이브 같은 글쓰기 기능 묶음으로 둔다.
- `v0.7.0` 은 블로그 이미지 업로드와 Flash Game 공간 같은 후속 기능 묶음으로 둔다.
- Flash Game 기능은 플레이어 통합과 게임 파일 수급/권리 확인을 같은 티켓으로 뭉개지 말고 나눠 적는다.
- 안정화 작업은 필요할 때 patch 또는 `v0.2.x` 티켓으로 추가한다.
- `infra` 와 `chore` 는 버전 상한과 무관하게 진행할 수 있다.

## 큰 minor 작업 쪼개기

`v0.3.0` 처럼 해야 할 일이 많은 minor 릴리스는 하나의 거대한 작업지시서로 만들지 않는다.

이 저장소는 아래 기준을 사용한다.

- 공식 릴리스 버전은 `v0.1.0`, `v0.1.1`, `v0.2.0` 처럼 깨끗한 SemVer 형식만 쓴다.
- `v0.2.0-branchA`, `v0.2.0-branchB` 같은 버전 문자열은 쓰지 않는다.
- 병렬 작업 구분은 버전 문자열이 아니라 `TKT 번호`, `권장 브랜치`, `선행 조건`, `Notes` 로 표현한다.
- 시작 가능 여부는 각 티켓의 `진행 판정` 으로 표현한다.
- 다음 minor에 들어가기 전 준비 작업은 현재 minor의 patch 슬라이스인 `v0.1.x` 로 나눈다.
- 현재 기준에서 `v0.3.0` 준비 작업은 `TKT-011`, `TKT-021`, `TKT-023` 같은 작은 체크포인트로 쪼갠다.
- `v0.3.0` 티켓은 엘리베이터 시뮬레이터 연동, 운행 제어, 첫 화면 UI 검증, 실시간 수요 분포와 연속 이동 감각 보강에 집중한다.
- `v0.4.0` 티켓은 Work Manager 메뉴, Jira 스타일 보드, `Backlog/Ready/Started/Need Review/Finished` 시각 흐름, 티켓 상세 패널, 티켓 이동/실행 브리지, command 비밀번호 게이트, 활동 로그 피드, 메타데이터 편집, Main page 라우팅, 다크모드, 테스트/CI/커버리지, PR 버전 가드로 쪼갠다.
- 버전이 붙는 PR 은 제목 또는 본문 첫머리에 대상 버전(`v0.4.0` 같은 SemVer 또는 `infra`/`chore`)을 반드시 드러내야 한다.
- 저장소 기본 PR 형식은 `.github/pull_request_template.md` 를 따르고, PR 제목은 `[v0.4.0]`, `[infra]`, `[chore]` 같은 prefix 로 시작한다.
- `tools/check-pr-version-metadata.ps1` 와 `.github/workflows/pr-version-guard.yml` 은 제목 prefix, 본문의 `Target Version`, `Feature Theme`, one-version-one-feature 체크리스트를 함께 검증한다.
- `v0.5.0` 티켓은 다양한 시뮬 포털 진입점, 택시 시뮬레이터 코어, 차량 투입 패널티와 처리시간 중심 보상, Work Manager worker 가시화, 우선순위 반응 실행, DB 전환으로 쪼갠다.
- `v0.5.1` 티켓은 사람 피드백 수집과 자동 학습 운영을 따로 둔다.
- `v0.6.0` 티켓은 블로그 허브, 글쓰기 스튜디오, Markdown 저장 계약과 렌더링 파이프라인으로 쪼갠다.
- `v0.7.0` 티켓은 블로그 이미지 업로드/미디어 처리와 Flash Game 공간, Ruffle 같은 플레이어 통합, 게임 카탈로그/합법 반입 경로로 쪼갠다.
- patch 슬라이스가 끝났다고 해서 `VERSION` 을 자동으로 올리지는 않는다. `VERSION` 은 사용자가 승인한 배포 완료 버전만 기록한다.

예시:

- `v0.1.2`: 런타임 정렬
- `v0.1.3`: 샘플 서비스 정리와 다음 서비스 계약 준비
- `v0.1.4`: 샘플 서비스 잔여 기본값 같은 릴리스 전 정밀 정리
- `v0.2.0`: `localhost:7000` 통합 프리뷰 릴리스 게이트
- `v0.3.0`: 엘리베이터 시뮬레이터를 플랫폼 프리뷰에 연결하는 다음 minor
- `v0.4.0`: Work Manager 메뉴와 티켓 보드/command 게이트를 붙이는 다음 minor
- `v0.5.0`: 택시 시뮬레이터 포털과 시뮬레이션 코어를 연결하는 다음 minor
- `v0.5.1`: 택시 시뮬레이터 피드백/학습 운영을 분리한 후속 슬라이스
- `v0.6.0`: 블로그 공간과 글쓰기/발행 흐름을 붙이는 다음 minor
- `v0.7.0`: 블로그 이미지 업로드와 Flash Game 공간을 여는 후속 minor

## 선행 조건 규칙

티켓은 필요하면 `선행 조건` 을 가질 수 있다.

예시:

- `v0.1.6` 티켓은 `v0.1.4` 티켓이 끝나야 시작할 수 있다.
- 공개 배포 티켓은 DNS 결정 티켓이 끝나야 시작할 수 있다.
- 프리뷰 연결 티켓은 서비스 스캐폴드 티켓이 끝나야 시작할 수 있다.

선행 조건이 있는 티켓은 아래 규칙을 따른다.

- 선행 조건이 끝나지 않았으면 worker는 티켓을 시작하지 않는다.
- 선행 조건이 불분명하면 worker는 작업을 진행하지 말고 Notes에 질문을 남긴다.
- 오케스트레이터는 선행 조건을 티켓의 `질문/결정 기록` 과 `Notes` 에 명확히 적는다.
- 선행 조건이 충족되면 오케스트레이터가 티켓 상태나 Notes를 갱신한다.

## 왜 Gradle 버전만 쓰지 않는가

이 저장소는 Vue, Spring Boot, Python/Go/Java 후보 서비스, 워커, 인프라 문서를 함께 담는 모노레포다. Gradle 또는 Maven 같은 단일 빌드 도구의 버전만으로 플랫폼 전체 개발 상한을 표현하면 프런트엔드, 워커, 인프라 티켓이 빠진다.

따라서 단일 빌드 도구 버전은 각 서브프로젝트의 패키징 버전으로만 사용하고, 플랫폼 운영 버전은 `VERSION`, `docs/releases.md`, 티켓 메타데이터 조합으로 관리한다.

## 릴리스 후 절차

1. 사용자가 배포 가능 여부를 명시한다.
2. 사용자가 `main` 병합을 완료한다.
3. 오케스트레이터는 최신 `main` 을 다시 가져온다.
4. `VERSION` 을 새 릴리스 버전으로 갱신한다.
5. `docs/releases.md` 에 릴리스 날짜, 태그, `main` 반영 여부, 요약, 후속 위험을 기록한다.
6. 다음 개발 상한과 후속 티켓을 정리한다.
7. 히스토리에 절차 결과를 남긴다.
