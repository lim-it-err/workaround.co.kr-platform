# 릴리스 목표

이 문서는 각 버전 트랙이 왜 존재하는지, 그리고 해당 버전에서 무엇이 완료 상태인지 작업자가 빠르게 이해할 수 있도록 정리한 기준 문서다.

## 릴리스 운영 원칙

- 릴리스 진행은 사용자가 명시적으로 배포를 승인했을 때만 진행한다.
- 공식 버전 기준은 `Git tag` 와 `GitHub Releases` 이다.
- `GitHub Packages` 는 필요할 때만 쓴다.
- 릴리스가 끝나면 `docs/releases.md` 에 릴리스 날짜, 태그, 요약, 주의사항을 기록한다.
- 릴리스가 끝나면 기본적으로 최신 `main` 을 다시 가져와 다음 작업 기준선을 맞춘다.
- `infra` 와 `chore` 티켓은 릴리스 버전과 무관하게 진행할 수 있다.
- 버전이 붙는 티켓은 현재 릴리스가 아니라 해당 티켓의 `target version` 을 따른다.
- 워커는 현재 릴리스와 다음 릴리스를 구분해서 읽고, 임의로 버전 경계를 올리지 않는다.

## 현재 릴리스 상태

- `v0.1.0`: 2026-06-13 릴리스 완료, `main` 병합 완료
- `v0.2.0`: 2026-06-13 릴리스 완료, `main` 반영 완료

## 현재 개발 상한

- 최신 배포 완료 버전: `v0.2.0`
- 버전 기능 작업: 다음 minor인 `v0.3.x` 까지
- 비버전 작업: `infra`, `chore`
- 다음 minor 후보: `v0.3.0`
- 예외: 사용자가 `localhost:7000` 확인 후 `v0.3.0` 선작업을 지시했으므로 `TKT-011` 같은 다음 minor 후보 작업은 미리 준비할 수 있다. 다만 `VERSION` 승격과 `v0.3.0` 릴리스 기준선 생성은 별도 승인 전까지 하지 않는다.

상세 규칙은 `docs/version-policy.md` 를 따른다.

## 릴리스 기록 방식

새 릴리스를 확정할 때는 아래 항목을 함께 남긴다.

- 릴리스 날짜
- 릴리스 태그
- `main` 반영 여부
- 핵심 변경 요약
- 남은 위험 또는 후속 티켓

GitHub Releases 를 쓰는 경우에도 `docs/releases.md` 를 기준 문서로 같이 갱신한다.
