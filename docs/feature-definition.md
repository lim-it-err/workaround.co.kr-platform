# 기능 정의서

## 목적

이 문서는 `v0.4.0` 부터 `v0.6.0` 까지의 사용자 경험, 기능 책임, 페이지 경계, 운영 규칙을 고정하는 기준 문서다.

이 저장소는 사용자 요청이 빠르게 누적되고, 디자이너 더미, 워커 구현, 오케스트레이터 티켓 정리가 동시에 움직인다. 그 결과 "지금 무엇이 진짜 제품 기준인가"가 흔들리기 쉬웠다. 앞으로는 이 문서를 제품 기준선으로 삼는다.

## 이 문서가 막아야 하는 흔들림

- 검수용 더미 UI 가 기본 사용자 경로를 덮어쓰는 일
- 메인 허브에 실제 기능 패널이 다시 섞여 들어오는 일
- Work Manager 를 단순한 화면 시안으로만 보고 실행 계약을 놓치는 일
- 엘리베이터 시뮬레이터가 승객 단위 모델에서 다시 호출 건수 단위 모델로 후퇴하는 일
- 택시 시뮬레이터 범위를 강화학습 연구와 웹 포털 구현이 뒤섞인 채 시작하는 일
- 워커가 티켓만 보고 구현하다가 페이지 책임과 제품 목적을 잘못 해석하는 일

## 적용 범위

- 제품 기준 범위: `v0.4.0`, `v0.5.0`, `v0.6.0`
- 연관 문서:
  - `docs/frontend-ux.md`
  - `docs/roadmap.md`
  - `docs/steering.md`
  - `docs/tickets/board.md`
  - `design/` 아래 UI/UX 기준 문서

세부 UI 연출은 `design/` 문서가 더 앞선다. 다만 페이지 책임, 기능 경계, 제품 목적은 이 문서가 기준이다.

## 제품 한 줄 정의

`workaround central` 은 서울 지하철식 환승 허브 감각을 가진 개인용 서비스 포털이다. 사용자는 메인 허브에서 기능을 고르고, 실제 시뮬레이터나 운영 기능은 각 승강장 페이지에서 수행한다.

## 공통 제품 원칙

### 1. 메인 허브와 기능 페이지를 섞지 않는다

- 메인 허브는 "요약 + 선택 + 이동"만 담당한다.
- 실제 조작은 기능 페이지에서만 일어난다.
- 메인 허브에 Work Manager 전체 보드나 Elevator 전체 dispatch 표를 직접 펼치지 않는다.

### 2. 검수 더미와 실사용 포털을 분리한다

- `/` 는 기본 사용자 경로다.
- `/test` 는 검수용 더미 경로다.
- `/test` 의 목적은 디자인 검수와 빠른 확인이지, 실사용 기능을 대체하는 것이 아니다.

### 3. 기능은 요약이 아니라 계약으로 정의한다

- "엘리베이터 화면"처럼 추상적으로 적지 않는다.
- 입력, 상태, 전이, 제약, 예외를 함께 적는다.
- worker 는 이 문서를 보고 제품 의도를 재해석하지 않고 구현할 수 있어야 한다.

### 4. 운영 화면도 제품의 일부다

- Work Manager 는 임시 관리자 도구가 아니라 제품의 한 기능 페이지다.
- 따라서 보기 좋은 더미가 아니라, 실제 티켓 조회/전이/명령 계약이 중요하다.

### 5. 유머는 기능을 해치지 않는 선에서만 사용한다

- 플랩 문구와 운영 피드는 생활감, 도시 감각, 가벼운 자기풍자를 가질 수 있다.
- 하지만 문구가 실제 상태 설명을 덮어쓰거나, 검수 지시문이 사용자-facing 카피를 침범하면 안 된다.

## 사용자 유형

현재 기준 사용자 유형은 아래 두 가지면 충분하다.

1. 일반 사용자
   - 메인 허브에서 기능을 고른다.
   - Elevator Station, Runtime Board 같은 공개 페이지를 본다.
- Work Manager 보드는 조회만 할 수 있다.
   - `Blog District` 공개 아카이브와 글 상세는 읽을 수 있다.

2. 운영 사용자
   - 같은 포털 안에서 Work Manager 상세 패널과 command gate 를 사용한다.
   - 실행성 액션은 비밀번호 게이트 뒤에서만 수행한다.

현재는 사용자가 한 명이라는 가정을 둔다.

필수 요소:

금지:

- Work Manager 5레인 전체 보드 직접 노출

- 택시/엘리베이터 실제 조작 패널을 허브 화면에 직접 펼치는 것

### 3. Elevator Station

목적:

- 23층 다중 엘리베이터 시뮬레이터를 실제로 조작하고 읽는 화면

도메인 기준:

- 건물은 23층
- 여러 대 엘리베이터가 동시에 움직인다
- 각 엘리베이터 정원은 20명
- 기본 단위는 호출 건수가 아니라 사람 수
- 각 사람은 출발층과 목적층을 가진다
- 상행/하행은 같은 비중으로 다룬다

입력:

- `한산`, `보통`, `혼잡` 수요 프리셋
- 수요 강도 슬라이더
- 엘리베이터 대수 조절
- `상행 1명 추가`
- `하행 1명 추가`
- 리셋

표시:

- 층별 대기 인원
- 주요 목적층
- car 별 현재 적재 인원
- 정원 20명
- car 내부 승객 수가 직관적으로 보이는 점/실루엣형 애니메이션
- 연속 위치 `position`
- 최근 도착 로그

행동 기준:

- 기본은 자동 운행
- `step` 은 있더라도 디버그 보조 제어로만 본다
- 움직임은 끊긴 step 보다 연속 운행처럼 느껴져야 한다
- 화면에서 같은 갱신 주기 안에 여러 층을 워프한 것처럼 보이면 안 된다
- 서비스 tick 이 거칠더라도 프런트 렌더링은 층 사이 진행이 자연스럽게 읽히도록 보간 또는 cadence 보정을 둔다

금지:

- 다시 hall call 건수 중심 화면으로 후퇴하는 것
- 목적층 없는 사람 모델
- 상행/하행 중 한쪽만 수동 추가 가능한 구조

### 4. Work Manager

목적:

- 티켓 흐름을 포털 안에서 조회하고, 제한된 운영 액션을 실행한다.

화면 구조:

- 5개 흐름: `Backlog`, `Ready`, `Started`, `Need Review`, `Finished`
- 상세 패널
- command zone
- activity feed
- 목표 버전 헤더 / 로드맵 요약

행동 기준:

- 이 5레인은 `docs/tickets/` 의 5개 폴더(`backlog/ready/started/need_review/finished`)와 1:1로 대응한다.
- 사용자가 직접 드래그하는 기본 전이는 `Backlog -> Ready` 이며, 오케스트레이터가 실제 파일 이동으로 확정한다.
- `Ready -> Started` 는 worker 소유 구간
- `Need Review -> Finished` 는 orchestrator/PM 소유 구간
- command 입력은 freeform 이 아니라 `preset action + memo`
- 실행성 액션은 비밀번호 게이트 뒤에서만 허용
- 보드 조회는 공개

상세 패널 필수 읽기 항목:

- 목표
- 작업 내용
- 선행 조건
- 질문/결정 기록
- Notes
- 검토 메모
- 대상 버전
- 우선순위
- 의존성

`v0.4.0` 에서 반드시 되는 것:

- 5레인 표시
- `Backlog / Ready` 시각 분리
- 티켓 클릭 상세 읽기
- preset command + memo
- 비밀번호 게이트
- activity feed

`v0.4.0` 에서 아직 후속으로 남기는 것:

- 실제 worker 할당자 이름 가시화
- 우선순위 변경 즉시 스케줄러 반영
- DB 기반 영속 저장

`v0.5.0` 에서 추가되는 것:

- Started 구간 worker ownership summary
- 우선순위 반응 규칙 요약
- 파일 기반 감사 로그와 DB 전환 기준선

### 5. Taxi District Lab

목적:

- 9구역 추상 도시 안에서 랜덤/수동 호출, 차량 배차, reward/penalty 루프를 읽고 조작한다.

입력:

- 출발지 선택
- 도착지 선택
- 인원수 1~4
- 차량 1대 추가

표시:

- 9구역 수요 카드
- active/completed request 목록
- 차량 상태 카드
- reward / penalty / net score

규칙:

- 별도 서비스 없이 프런트 단독 시뮬레이션으로 시작한다.
- 가장 가까우면서 정원 여유가 있는 idle 차량을 우선 배차한다.
- 차량 추가는 즉시 penalty 로 누적한다.

### 6. Blog District

목적:

- 공개 글 읽기와 단일 작성자 글쓰기를 포털 안의 별도 라인으로 분리한다.

하위 페이지:

- `Blog District` 허브
- `Public Archive`
- `Post Detail`
- `Writing Studio`

규칙:

- `published` 만 공개 아카이브와 글 상세에 노출한다.
- `draft` 와 `archived` 는 Studio 상태 흐름 안에서만 관리한다.
- 읽기 화면은 시뮬레이터 패널보다 문서형 폭과 typography 를 우선한다.

### 5. Runtime Board

목적:

- 시스템/노드/릴리스 상태를 운영 관점에서 요약한다.

필수 요소:

- `ion2`, `rtx5070`, `gateway` 역할
- degraded 정책
- release path 요약
- Ollama 상태 요약

금지:

- 인프라 세부 운영 매뉴얼 전체를 이 화면에 쏟아 넣는 것

## 버전별 기능 정의

## `v0.4.0`

`v0.4.0` 의 제품 테마는 "운영 가능한 포털 구조 복구"다.

즉 다음을 동시에 만족해야 한다.

- Main page 와 기능 페이지 경계가 분명하다
- Elevator Station 이 살아 있는 기능 페이지다
- Work Manager 가 조회/실행 계약을 가진 운영 페이지다
- `/test` 더미가 `/` 실사용 포털을 덮어쓰지 않는다
- 테스트 코드 / CI / 커버리지 / PR 버전 가드까지 포함한다

`v0.4.0` 에 포함되는 티켓:

- `TKT-031`
- `TKT-032`
- `TKT-033`
- `TKT-034`
- `TKT-036`
- `TKT-037`
- `TKT-039`
- `TKT-040`
- `TKT-041`
- `TKT-046`

### `v0.4.0` 완료 판정

아래가 모두 만족되어야 한다.

1. 메인 허브 / Elevator / Work Manager / Runtime 이 페이지 책임상 분리되어 있다.
2. 플랩 문구가 회귀하지 않았다.
3. Work Manager 는 최소한 조회, Ready 시각 분리, 상세 읽기, preset command gate 를 가진다.
4. 테스트 코드와 GitHub Actions 경로가 있다.
5. 커버리지 노출 경로가 README 와 문서에 적혀 있다.
6. PR 버전 표기 규칙이 문서뿐 아니라 실질 가드로 연결된다.

## `v0.5.0`

`v0.5.0` 의 제품 테마는 "시뮬레이션 포털 확장"이다.

즉 `v0.4.0` 포털 구조 위에서, 새로운 시뮬레이션 축을 추가한다.

포함 범위:

- 다양한 시뮬레이터 포털 진입 구조
- 택시 시뮬레이터 코어
- Work Manager 후속 운영 기능 일부

### 시뮬레이터 포털

목적:

- Elevator 외의 시뮬레이터를 허브 안에서 확장 가능하게 연다.

필수 조건:

- Main Junction 또는 그 후속 허브 구조 안에서 택시 시뮬레이터 진입점이 보인다.
- Elevator 와 Taxi 는 같은 카드가 아니라 별도 기능 페이지로 분리된다.

### 택시 시뮬레이터 코어

목적:

- 가상 지도 위에서 수요와 차량 배치를 다루는 게임/시뮬레이션을 만든다.

도메인 기준:

- 가상의 지도가 있다
- 랜덤 요청이 발생한다
- 사용자가 수동으로 출발지/도착지/인원수를 넣을 수 있다
- 인원수에 따라 적절한 택시가 이동한다
- 처리 시간은 리워드에 반영된다
- 차량을 추가 배치하면 리워드가 깎인다

제품 관점의 최소 구현:

- 자유 좌표보다 단순한 구역 기반 시각화를 우선한다
- 요청 생성
- 차량 상태 표시
- 처리 시간 측정
- 리워드 계산 표시
- 첫 구현은 프런트 단독 시뮬레이션 코어로 시작할 수 있다

후속 분리:

- 강화학습 학습 파이프라인
- RTX5070 평가/피드백 루프
- 사람 피드백 수집과 자동 학습 운영

즉 `v0.5.0` 은 "게임/시뮬레이션 코어와 포털 진입점"까지다. 학습 운영은 `v0.5.1` 이다.

### Work Manager 후속 확장

`v0.5.0` 에 열리는 운영 확장:

- 어느 worker 가 무엇을 잡았는지 표시
- 우선순위 메타데이터와 실제 실행 반응의 연결 설계
- 파일 기반 저장에서 DB 전환 준비

## 구현 가드레일

### 오케스트레이터

- 티켓을 만들거나 수정할 때 이 문서의 기능 경계를 기준으로 쪼갠다.
- 기능 정의와 어긋나는 더미/시안은 `/test` 또는 `design/` 문서로 격리한다.
- worker 가 혼동할 수 있는 부분은 티켓의 `질문/결정 기록` 에 이 문서 내용을 그대로 풀어 적는다.

### worker

- 티켓 구현 전에 이 문서를 읽는다.
- 티켓이 이 문서와 충돌하면 임의 구현하지 않고 Notes 또는 review 메모로 올린다.
- 페이지 책임을 바꾸는 구현은 오케스트레이터 재확인 없이 진행하지 않는다.

### designer

- 시안은 자유롭게 만들 수 있지만, 기본 사용자 경로를 덮어쓰는 변경은 이 문서와 티켓 acceptance 를 같이 갱신해야 한다.

## 실험 놀이터 확장 (발견 노선 / 취향 노선)

2026-07-05 사용자 요청으로 실험 놀이터 정체성을 강화하는 두 기능 페이지를 추가한다. 상세 설계는 각 정의서를 따른다.

### Line D · 발견 노선 (Discovery)

- 매일 랜덤 주제 하나를 발견하고, 3방향(더 깊이/더 넓게/뜻밖의 각도)으로 최대 depth 3까지 파고드는 학습 놀이터.
- depth 0~1 은 정적 데이터(주제 100개), depth 2~3 은 Claude API 온디맨드 + 캐싱.
- 상세: `docs/discovery-line-definition.md`. 대상 버전 `v0.8.0`.

### Line P · 취향 노선 (Palate/Taste)

- 10개 A/B 선택으로 취향 벡터를 만들어 와인 1종 + 커피 1종을 규칙 기반으로 추천. 조합 폭발(2^10) 없이 와인 24·커피 24 프로파일 최근접 매칭.
- 런타임 토큰 0(정적). 추천 이유 심화 설명만 선택적 API.
- 상세: `docs/taste-line-definition.md`. 대상 버전 `v0.9.0`.

## 변경 관리 규칙

- 기능 정의가 바뀌면 이 문서를 먼저 바꾸거나, 같은 변경 안에서 함께 바꾼다.
- 이 문서에 정의된 기능 페이지를 건드리는 티켓은 버전과 무관하게 이 문서를 선행 읽기에 포함한다.
- 오케스트레이터는 리뷰 때 "코드가 맞나"만 보지 않고 "기능 정의와 맞나"를 먼저 본다.
