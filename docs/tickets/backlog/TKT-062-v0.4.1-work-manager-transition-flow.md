# TKT-062

## 메타데이터

- 제목: Work Manager 전이 흐름 정렬 (ready 단계 수명주기 + UI 도달성)
- 우선순위: P2
- 대상 버전: `v0.4.1`
- 상태: `backlog`
- 문서 상태: `작성완료`
- 진행 판정: `진행 가능`
- 소유자 유형: `worker`
- 권장 브랜치: `codex/tkt-062-work-manager-transition-flow`

## 목표

Work Manager 전이 계약을 명확히 하고, 게이트웨이 전이 매트릭스를 새 ready 단계 수명주기(`backlog -> ready -> started -> need_review -> finished` + `need_review -> backlog`)에 정렬한다. UI 에서 전이가 도달 불가한 문제와 TKT-032 검토 메모의 허위 완료 주장을 바로잡는다.

## 작업 내용

1. [MAJOR] 게이트웨이 전이 매트릭스를 새 수명주기에 정렬 (#4)
   - `validateWorkManagerTransition` (`gateway/src/main/java/com/workaround/platform/gateway/PlatformGatewayApplication.java:1244-1261`) 은 현재 `backlog -> started`, `started -> need_review`, `need_review -> finished` 순방향만 허용하고 나머지는 409 를 던진다. 문서화된 재작업 반려 `need_review -> backlog` 도 거부한다.
   - `docs/ticket-policy.md:107` 의 목표 매트릭스에 맞춘다: `backlog -> ready`, `ready -> started`, `started -> need_review`, `need_review -> finished` 순방향 + 검토 반려 `need_review -> backlog`. (`started -> backlog` 재작업 직접 전이 허용 여부는 질문/결정 기록 참조.)
   - `validateTransitionGate` (`gateway/.../PlatformGatewayApplication.java:1263-1282`) 의 진행 판정 게이트가 현재 `started` 전이에만 걸려 있다. 새 매트릭스에서는 `ready` 승격과 `started` 착수 중 어디에 게이트를 걸지 재검토한다(기본: `ready` 승격 게이트).
   - `persistWorkManagerTransition` (`gateway/.../PlatformGatewayApplication.java:1284` 이하)의 대상 폴더 이동이 새 상태 전이(특히 `need_review -> backlog` 역방향)와 일치하는지 확인한다.

2. [MAJOR] UI 전이 도달성과 TKT-032 허위 완료 주장 정리 (#3)
   - 현재 프론트는 `/transition` 을 전혀 호출하지 않는다. `Backlog <-> Ready` 드래그가 localStorage 만 갱신한다: `frontend/src/App.vue:1737-1755`, drop 핸들러 `:3974`, draggable `:3991`.
   - 이는 finished/TKT-032 검토 메모(`docs/tickets/finished/TKT-032-v0.4.0-ticket-transition-and-command-bridge.md:73`, 완료 기준 `:36`)가 전이가 서버에 wired 되었다고 주장하는 것과 모순된다. 서버 transition / worker-bridge / board.md rewrite / audit 가 UI 에서 전부 dead 다.
   - `docs/feature-definition.md:209-211` 은 사용자가 직접 드래그하는 기본 전이를 `Backlog -> Ready` 로 두고 나머지 레인 전이는 시스템(worker/orchestrator) 소유로 규정한다.
   - 결정된 계약(질문/결정 기록)에 따라: (기본) 사용자 `Backlog -> Ready` 조작이 서버 `/transition` 을 실제로 호출하도록 wire 하거나, 현행 제안(localStorage)만 유지하는 계약을 유지하되 어느 쪽이든 UI/문서 표기와 일치시킨다. 그리고 TKT-032 의 "wired" 주장이 실제와 다르므로 정정 근거를 남긴다(문서 상태 재판정은 오케스트레이터 확정 대상이므로 Notes 로 이관).

## 범위

- 포함: 게이트웨이 전이 매트릭스의 새 수명주기 정렬, `Backlog -> Ready` 전이의 서버 연동 결정 및 반영, 전이 계약 명확화, 전이 테스트 추가(TKT-064 와 조율)
- 제외: 인증 하드닝(TKT-060), 세션 UX(TKT-061), 저장소 정합(TKT-063), 동시성/원자적 쓰기(TKT-064). TKT-032 문서 자체의 상태 재판정은 오케스트레이터 확정 대상.

## 완료 기준

- 게이트웨이가 `need_review -> backlog` 재작업 반려를 허용한다(더 이상 409 아님). (런타임 체크: rework 409 해소)
- 새 매트릭스의 합법 전이(`backlog -> ready -> started -> need_review -> finished`, `need_review -> backlog`)는 통과하고, 불법 전이는 409 로 거부된다. (런타임 체크: transition UI reachability)
- 사용자의 `Backlog -> Ready` 조작이 서버 상태/보드에 반영되거나, 반영하지 않는 계약이라면 그 사실이 UI/문서에 정확히 표기된다.
- TKT-032 의 전이 wired 주장과 실제 동작 사이의 불일치가 해소된다(정정 근거 포함).
- 새 매트릭스에 대한 합법/불법 전이 테스트가 추가된다(TKT-064 와 정합).

## 질문/결정 기록

- 결정(`docs/ticket-policy.md:107`): 목표 전이 매트릭스는 `backlog -> ready -> started -> need_review -> finished` 순방향 + `need_review -> backlog` 검토 반려다. 이 티켓은 게이트웨이 코드를 이 정책에 맞춘다.
- 열린 질문: `started -> backlog` 재작업 직접 전이를 허용할지. 기본은 미허용(재작업은 `need_review -> backlog` 경유).
- 열린 질문: 사용자 `Backlog -> Ready` 드래그를 서버 `/transition` 으로 승격할지, 제안(localStorage)만 유지하고 오케스트레이터가 파일 이동으로 확정하는 현행 계약을 유지할지. `docs/feature-definition.md:210` 은 후자를 시사하나, 이 경우 TKT-032 의 "wired" 주장은 반드시 정정해야 한다.
