## 목표

`v0.3.1`(TKT-049)에서 완화만 했던 엘리베이터 warp/배차 문제의 서비스측 근본 원인을 고친다. 특히 car 수 조절이 시뮬 전체를 초기화하는 CRITICAL 버그(사용자 보고)와, 클라이언트 poll 시점에만 시뮬이 진행되어 화면에 보이는 다층 warp 를 만드는 근본 원인을 해결한다. 모든 수정은 `services/elevator-service/app.py`(문서 정합은 `services/elevator-service/README.md`) 안에서 이루어진다.

## 작업 내용

각 항목은 QA 발견(2026-07-05)과 1:1로 대응한다. 인용한 `file:line` 은 착수 시점 기준이며, 리팩터로 줄이 밀리면 동일 함수/블록을 기준으로 판단한다. 프런트(`App.vue`, `styles.css`) 수정은 이 티켓 범위가 아니고 TKT-059 에서 다룬다. 아래에 나오는 프런트 `file:line` 은 원인/증상 추적용 참고다.

1. [CRITICAL · 사용자 보고] car 수 슬라이더가 시뮬 전체를 지운다.
   - 위치: `services/elevator-service/app.py:655-675`(`configure_elevators`)가 `services/elevator-service/app.py:93-124`(`initial_state`)로 새 상태를 만들고 `STATE.clear()` + `STATE.update(fresh_state)`(`app.py:673-674`)로 통째 교체한다.
   - 트리거 경로: 프런트 `frontend/src/App.vue:1270-1277`, UI 컨트롤 `frontend/src/App.vue:3218-3228`.
   - 증상: 탑승 중이던 승객이 completed 로그도 없이 파괴되고, 대기열이 비며, `tick` 이 0 으로 돌아가고, car 가 시작 층으로 순간이동한다. TKT-049 는 "재배치(repositioning)"만 승인했지 재초기화는 승인한 적이 없다.
   - 수정 방향: `initial_state` 재호출로 통째 교체하지 말고 기존 `STATE` 를 mutate 한다. car 를 개수 변화만큼 추가/제거하고, 제거되는 car 에 타고 있던 승객은 대기열로 requeue 한다. `tick`, `demand`, `completed`, 유지되는 car 상태는 절대 초기화하지 않는다.

2. [MAJOR · 화면 warp 의 근본 원인] 시뮬이 클라이언트 poll 시점에만 진행된다.
   - 위치: `services/elevator-service/app.py:576-585`(`sync_state`)가 catch-up step 을 `clamp(steps, 1, 96)`(`app.py:582`)로 최대 96틱까지 한 번에 몰아 실행한다. 시뮬을 돌리는 백그라운드 스레드가 없다(`services/elevator-service/app.py:790-793`).
   - poll: `frontend/src/App.vue:1201-1203`(900ms 간격).
   - 증상: 탭이 백그라운드로 갔다가/멈췄다가 돌아오면 다음 poll 한 번이 최대 96 step(≈17층)을 한꺼번에 진행시키고, 그 이동량이 CSS transition 하나에 실려 눈에 보이는 THE WARP 로 나타난다. 공백이 33.6초를 넘으면 96-step poll 이 여러 번 연속으로 발생한다.
   - 수정 방향(둘 중 하나, 기본안은 A):
     - A) 서비스에 백그라운드 step 스레드를 두어 시뮬 시간을 클라이언트 poll 과 분리한다. poll(스냅샷 조회)은 상태를 읽기만 하고 더 이상 `step_once` 로 시간을 밀지 않게 한다. 이 안은 서비스 단독으로 닫힌다.
     - B) A 가 어려우면 catch-up 을 작은 상한으로 clamp 하고, 큰 tick delta 가 발생하면 프런트가 transition 없이 snap 하도록 스냅 신호(예: 큰 이동 플래그/틱 버전)를 스냅샷에 실어 보낸다. B 를 택하면 프런트 snap 처리가 필요하므로 TKT-059 와 조율해야 한다.

3. [MAJOR] 배차 재할당이 유령 정차와 방향 flapping 을 만든다.
   - 위치: `services/elevator-service/app.py:322-331`(`reassign_waiting_passengers`), 호출 지점 `services/elevator-service/app.py:571` 및 `services/elevator-service/app.py:341`(매 틱). 출발 층을 `services/elevator-service/app.py:205-211`(`ensure_floor_in_queue`, append-only)로 다시 넣지만 이전 car 의 큐에서는 제거하지 않는다. `services/elevator-service/app.py:179-194`(`score_elevator`)는 idle car 페널티가 없어(`app.py:194`) idle car 가 운행 중 호출을 가로챈다.
   - 증상: 빈 층에서의 유령 정차, 방향 flapping, throughput 하락, backlog 증가.
   - 수정 방향: 재할당 시 이전 car 의 큐에서 출발 층을 제거한다(그 car 에 여전히 필요한 경우는 예외). inbound car 에 히스테리시스를 두어 idle car 가 en-route 호출을 뺏지 않게 한다.

4. [MINOR] `waitingPassengers` 리스트가 무한히 커진다.
   - 위치: completed 는 `services/elevator-service/app.py:283-284`에서 24/12 로 캡되지만 waiting 은 캡이 없다. 전체 리스트가 매 스냅샷마다 `services/elevator-service/app.py:438`에서 직렬화된다.
   - 증상: 지속 수요 하에서 payload 와 메모리가 계속 증가한다.
   - 수정 방향: waiting 을 캡하거나 병합한다. UI 는 `floorQueues` 를 쓰므로 raw waiting 리스트는 스냅샷에서 빼는 것을 기본안으로 한다.

5. [MINOR] `movingElevators` 카운트가 문 열림(dwell) 중 과다 집계된다.
   - 위치: `services/elevator-service/app.py:336-342`(`service_floor`)가 문을 open 으로 둔 직후 `services/elevator-service/app.py:165-177`(`set_elevator_direction`)이 status 를 다시 moving 으로 되돌린다. 요약이 moving 을 `services/elevator-service/app.py:401`에서 센다.
   - 프런트 표시(증상 확인용 참고): 배너 `frontend/src/App.vue:3167-3168`, glyph `frontend/src/App.vue:1723-1727` 및 `frontend/src/App.vue:3265`.
   - 증상: 정차마다 한 poll 동안 moving 카운트가 깜빡인다.
   - 수정 방향: `doorState == open` 인 동안에는 moving 재할당(상태를 moving 으로 되돌리는 처리)을 건너뛴다.

6. [COSMETIC] 자동 스폰 예산이 초과분을 조용히 버린다.
   - 위치: `services/elevator-service/app.py:507-526`(`auto_spawn_passengers`)가 정수 예산 전체를 차감하지만 실제로는 최대 4명만 스폰한다. batched catch-up 중 초과분이 사라진다.
   - 수정 방향: 실제로 스폰한 수만 예산에서 차감한다.

7. [MINOR] 문서 정합(doc drift) 정리 — `services/elevator-service/README.md`.
   - `MOVE_STEP_PER_TICK`: README 는 0.25, 코드는 0.18(`services/elevator-service/app.py:17`).
   - 프리셋 이름: README 는 quiet/normal/busy, UI 는 commute/lunch/evening(`frontend/src/App.vue:3188`), 백엔드는 6종을 지원한다(`services/elevator-service/app.py:22-29`, `DEMAND_PRESETS`).
   - `/api/config` 엔드포인트가 README 에 문서화돼 있지 않다. 프런트가 의존하고(`frontend/src/App.vue:1273`), 게이트웨이 프록시가 포워딩한다(`gateway/src/main/java/com/workaround/platform/gateway/PlatformGatewayApplication.java:132-141`, 범용 `proxyService` 경로).
   - 수정 방향: README 를 실제 코드 상수/프리셋 이름/엔드포인트에 맞춰 정합화한다. 코드를 README 에 맞추는 게 아니라 문서를 코드에 맞춘다.

## 완료 기준

기능 기준:

- car 수를 2~6 사이에서 바꿔도 탑승/대기 승객, `tick`, `completed`, demand 가 보존되고 car 는 순간이동하지 않는다(#1).
- 탭을 오래 백그라운드에 뒀다 돌아와도 car 가 한 번에 여러 층을 warp 하지 않는다(#2).
- 유령 정차(빈 층 정차)와 방향 flapping 이 눈에 띄게 줄고 backlog 가 무한히 늘지 않는다(#3, #4).
- 정차 시 moving 카운트가 한 poll 동안 튀지 않는다(#5).
- 배치 catch-up 상황에서도 스폰 예산이 실제 스폰 수와 일치한다(#6).
- README 의 `MOVE_STEP_PER_TICK`, 프리셋 이름, `/api/config` 기술이 코드와 일치한다(#7).

런타임 확인(QA 의 "runtime checks" 를 인수 검사로 사용):

- car 수 리셋 재현: 승객이 탄 상태에서 슬라이더를 움직여 승객/`tick`/`completed` 가 보존되는지 확인.
- 40초 탭 백그라운드 warp: 탭을 40초 이상 백그라운드로 두었다가 복귀해 다층 점프가 사라졌는지 확인.
- 배차 flap 로깅: 한 호출이 car 사이를 왕복 재할당하지 않는지 로그로 확인.
- backlog 증가 감시: 지속 수요에서 waiting/큐가 계속 증가하지 않는지 확인.
- moving flicker poll: 정차 순간의 연속 poll 에서 moving 카운트가 튀지 않는지 확인.
- `frontend` build 와 `elevator-service` smoke(또는 동등 검증) 결과를 남긴다.
