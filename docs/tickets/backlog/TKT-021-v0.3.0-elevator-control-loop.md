# TKT-021

## 메타데이터

- 제목: 23층 다중 엘리베이터 dispatch loop
- 우선순위: P2
- 대상 버전: `v0.3.0`
- 상태: `backlog`
- 문서 상태: `작성완료`
- 진행 판정: `진행 가능`
- 소유자 유형: `worker`
- 권장 브랜치: `codex/tkt-021-elevator-control-loop`

## 목표

`TKT-011` 이 연결한 엘리베이터 프리뷰를, 23층과 4대 엘리베이터가 동시에 상태를 가지는 다중 dispatch baseline 으로 검토 가능하게 정리한다.

## 이번 작업 결과

- `services/elevator-service/app.py` 의 현재 모델이 23층 / 4대 그룹 상태를 유지하는지 다시 검증했다.
- `tools/check-elevator-dispatch-baseline.ps1` 를 추가해 auto demand 를 끈 deterministic baseline smoke 를 남겼다.
- backlog 에 남아 있던 깨진 티켓 문서를 복구하고, 현재 코드와 남은 review 이슈를 기준으로 `need_review` 문서로 다시 정리했다.

## 작업 내용

- `services/elevator-service/app.py` 의 핵심 dispatch baseline 을 다시 확인했다.
  - 층 범위: `1F` ~ `23F`
  - 기본 엘리베이터 수: `4`
  - 기본 시작층: `1F`, `8F`, `16F`, `23F`
  - `POST /api/call` 로 legacy hall call 을 승객 생성 경로로 유지
  - `POST /api/step` 으로 전체 그룹을 한 tick 씩 전진
- `tools/check-elevator-dispatch-baseline.ps1` 에서 아래 검증 흐름을 자동화했다.
  - `POST /api/reset`
  - `POST /api/demand` with `autoMode=false`, `intensity=0`
  - `POST /api/call` for `12F/down`, `3F/up`
  - `POST /api/step` two times
  - `GET /api/state`
  - `POST /api/reset`
- 프런트 build 와 서비스 syntax check 를 다시 함께 확인했다.

## 범위

- 23층 / 4대 dispatch baseline 을 재현 가능한 상태로 검증한다.
- 다중 엘리베이터 배정, tick 진행, 초기 위치 reset 근거를 남긴다.
- 승객 단위 실시간 수요와 연속 이동의 확장은 `TKT-035` 와 구분해서, 이 티켓에서는 baseline dispatch 계약만 정리한다.
- gateway Java/Maven compile, gateway Docker build, 인앱 브라우저 시각 검수는 review 단계의 남은 제약으로 유지한다.

## 검토 메모

- deterministic 스모크를 위해 baseline 검증에서는 auto demand 를 껐다. 그렇지 않으면 자동 승객 생성 때문에 hall call 수가 흔들릴 수 있다.
- `TKT-035` 가 이미 승객 단위 실시간 수요와 연속 이동을 확장했기 때문에, `TKT-021` 은 baseline 계약과 재현 가능한 dispatch 증거를 남기는 역할로 정리했다.
- 현재 세션에서는 `java`, `mvn`, `docker` 가 없어 gateway compile / Docker build 는 미검증이다.
- 인앱 브라우저 기반 시각 검수는 Windows sandbox 의 `CreateProcessAsUserW failed: 5` 제약 때문에 자동 확인하지 못했다.
- 오케스트레이터 판정: dispatch baseline 스크립트는 통과했지만, 통합 프리뷰 기준의 gateway/browser 검증이 닫히지 않아 backlog 로 되돌린다.
