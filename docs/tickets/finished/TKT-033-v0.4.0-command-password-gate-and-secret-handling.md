# TKT-033

## 메타데이터

- 제목: command 비밀번호 게이트와 secret 해시 처리
- 우선순위: P1
- 대상 버전: `v0.4.0`
- 상태: `finished`
- 문서 상태: `작성완료`
- 진행 판정: `진행 가능`
- 소유자 유형: `worker`
- 권장 브랜치: `codex/tkt-033-command-secret-gate`

## 목표

아무나 Work Manager 의 command 창과 실행성 있는 티켓 이동을 쓰지 못하도록, 초기 공유 비밀번호 `xptmxldxptmxld` 를 서버측 secret 검증 구조로 넣고 평문 노출을 피한다. 조회 전용 보드는 계속 공개로 둔다.

## 작업 내용

- command 창과 실행성 있는 티켓 이동에만 비밀번호 게이트를 건다.
- 비밀번호 원문 `xptmxldxptmxld` 는 frontend 코드에 하드코딩하지 않는다.
- gateway 또는 backend 환경변수에 secret 또는 해시값으로 저장하고 비교한다.
- 기본안은 salt 포함 해시 또는 최소한 일방향 해시 비교다.
- 인증 성공 시 일정 시간 유효한 세션 또는 토큰을 발급해 매번 비밀번호를 다시 치지 않게 할지 검토한다.
- 실패 횟수 제한, 오류 메시지, 로그 최소 기준을 정한다.
- 문서에는 "초기 공유 비밀번호"라는 운영 성격과 교체 경로를 남긴다.

## 범위

- 포함: 비밀번호 입력 UI, backend secret 검증, 해시/암호화 저장 기준, 보호 대상 액션 정의, 공개 조회와 보호 액션의 경계 정의, 문서 갱신.
- 제외: 사용자 계정 시스템, OAuth, 관리자 권한 체계, 복수 사용자 RBAC.

## 완료 기준

- command 창은 인증 전에는 입력 또는 실행이 차단된다.
- 실행성 있는 티켓 이동도 같은 보호 정책 또는 명시된 보호 범위 안에 있다.
- 보드 조회와 활동 로그 조회는 인증 없이 가능하다.
- 비밀번호 원문이 frontend bundle 과 공개 문서에 직접 남지 않는다.
- secret 저장 방식과 교체 절차가 문서화되어 있다.

## 선행 조건

- `TKT-031` Work Manager 화면 구조가 먼저 준비되어야 한다.
- `TKT-032` command 브리지 또는 티켓 실행 액션 지점이 정의되어야 한다.
- 사용자 승인 없이 임의의 외부 인증 시스템을 붙이지 않는다.

## 질문/결정 기록

- 결정: 초기 비밀번호 문자열은 `xptmxldxptmxld` 로 둔다.
- 결정: 이 값은 frontend 에 박지 않고 server-side secret 검증으로 처리한다.
- 결정: 티켓 조회(read)와 활동 로그 조회는 공개로 둔다.
- 열린 질문: 인증 성공 후 세션 유지 시간을 얼마로 둘지.

## 검토 메모

- `POST /api/work-manager/auth` 를 추가해 공유 비밀번호를 서버측 SHA-256 해시와 비교하고, 짧은 Work Manager 세션 토큰을 발급하도록 구현했다.
- `X-Work-Manager-Token` 이 없는 상태에서는 티켓 전이와 preset command 실행이 차단되도록 gateway 와 frontend 흐름을 함께 연결했다.
- 실패 횟수 제한과 잠금 시간은 `WORK_MANAGER_MAX_FAILED_ATTEMPTS`, `WORK_MANAGER_LOCK_MINUTES`, `WORK_MANAGER_SESSION_TTL_MINUTES` 환경 변수로 조절하도록 정리했다.
- 기본 공유 비밀번호 평문은 코드에 두지 않고 `WORK_MANAGER_PASSWORD_SHA256` 기본값에 SHA-256 해시만 남겼다.
- `powershell -ExecutionPolicy Bypass -File .\tools\run-frontend-build.ps1` 검증은 통과했다.
- 현재 작업 환경에는 `java`, `mvn`, wrapper 가 없어 gateway compile 검증은 아직 못 했다.

## Notes

- "암호화"는 frontend 에 비밀번호를 숨기는 문제가 아니라, backend 에서 평문 저장을 피하고 비교하는 문제로 읽는다.
- 공유 비밀번호는 임시 운영 수단이므로 후속 버전에서 교체/회수 경로를 검토해야 한다.
