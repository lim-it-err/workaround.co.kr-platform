## 문제
균등 간격 도착이면 이용률 100% 미만에서 대기가 항상 0 이라 학습 문항 3("임계 이용률")의 답이 100% 로 고정된다. 실제 큐는 확률 도착 때문에 70~90% 부터 대기가 커진다.

## 목표
1. 도착 간격을 **시드 고정 지수분포**(예: mulberry32 시드 + `-ln(u)/λ`)로 — 같은 조건이면 같은 결과(재현성 유지). 처리시간은 고정 유지(또는 소폭 분산, 구현자 선택).
2. 결과에 이용률과 함께 대기가 커지는 구간이 보이도록 — 11시(3.6/분)·창구 3 에서 평균 대기 > 0, 창구 1 에서 폭발.
3. `대기 중` → `시간 내 미처리`(시작 시각 > 3600초)로 의미 있게 바꾸거나 숨김.
4. 결과 설명 문구를 "시드 고정 확률 도착" 으로 갱신.

## 완료 조건

2. [x] 이용률 50%→70%→90% 순으로 평균 대기 단조 증가(unit, 시드 고정).
3. [x] 기존 E2E 그린, 375/1440 overflow 0.

## 구현 내역

- `mulberry32` 고정 시드 `19000511`과 지수분포 간격 `-ln(u)/λ`를 사용해 한 시간 안의 확률 도착 시각을 만든다. 같은 조건은 도착 수·대기·미처리까지 완전히 같은 결과를 낸다.
- 표기 처리시간 고정과 즉시 다음 배정 계약은 유지했다. 한 시간 안에 도착했지만 처리 시작 시각이 3600초를 넘는 인원을 `시간 내 미처리`로 집계하고, 화면의 기존 `대기 중`을 `시간 내 처리 시작`·`시간 내 미처리`로 명확히 나눴다.
- 결과 설명을 `고정 시드 확률 도착`과 지수분포·무이동·무양자화 가정으로 갱신했다. 콘텐츠 3파일과 공용 택시 엔진은 수정하지 않았다.

## 검증

- 같은 11시 조건을 두 번 실행한 결과 객체가 동일함을 unit으로 고정했다.
- 고정 시드 합성 조건에서 이용률 `50% → 70% → 90%`, 평균 대기 `20초 → 57초 → 125초`로 단조 증가했다.
- 실제 콘텐츠 11시·창구 3개·예약 35%는 도착 209명, 이용률 69%, 평균 대기 12초·최장 64초였다. 창구 1개는 평균 1922초·최장 3621초, 시간 내 미처리 105명으로 포화를 드러냈다.
- Advisor unit 77/77, Chromium E2E 40/40, 기본·Pages advisor-base build 각각 110 modules 통과. 초기 JS 502.41kB 청크 경고는 기존 위험으로 유지한다.
- 375px dark·1440px light에서 11시 결과를 직접 확인했고 가로 overflow 0. 모바일의 6개 지표는 2열, 데스크톱은 1행으로 읽히며 조작부와 결과가 겹치지 않았다.
- Safari/WebKit·실제 Pages 배포는 미검증. commit/push 없음.
