# 스티어링 기록

이 문서는 대화 중 나온 운영 원칙과 아직 조정이 필요한 항목을 한곳에 모으는 기록이다.

## 확정된 원칙

- 오케스트레이터는 `TKT-018` 릴리스 게이트가 닫힐 때까지 `v0.2.0` 상태를 계속 점검하고, 사용자가 명시적으로 연 `v0.3.0` 및 `v0.4.0` 이하 선작업은 별도로 관리한다.
- 모든 규칙과 원칙은 관련 `docs/` 문서에 남긴다.
- 무리인 것, 현재 바로 할 수 없는 것, 다시 검토가 필요한 것, 사용자 결정이 필요한 것은 오케스트레이터가 먼저 사용자에게 알리고 문서와 티켓에 기록한다.
- 워커는 티켓의 `target version` 과 현재 개발 상한을 보고 작업한다.
- `infra` 와 `chore` 는 버전 상한과 무관하게 진행할 수 있다.
- 사용자가 명시적으로 배포를 승인하기 전에는 릴리스를 진행하지 않는다.
- 릴리스 완료 후 최신 `main` 을 다시 가져오고 문서와 히스토리를 갱신한다.
- `v0.1.0` 만 릴리스 완료 및 `main` 반영 완료 상태다.
- `v0.2.0` 은 로컬 프런트/서비스 검증이 진행된 조건부 후보이며, 아직 정식 릴리스 완료 상태가 아니다.
- 샘플 Python 서비스는 필수 서비스가 아니다.
- 엘리베이터 서비스는 Python, Go, Java 등 적합한 언어로 만들 수 있다.
- 서비스의 최종 실행 계약은 Docker 기반을 기본으로 한다.
- 티켓 간 전달 메모는 `Notes` 로 남긴다.
- `workaround.co.kr` 과 `workaround.kr` 공개 웹사이트 호스팅이 1차 목표다.
- 첫 공개 웹사이트는 플랫폼 소개 페이지를 우선한다.
- 대표 도메인은 `workaround.co.kr` 이다.
- 첫 공개 배포는 사용자가 가진 서버 위 Docker 배포를 기본으로 한다.
- 엘리베이터 시뮬레이터 본 구현은 `v0.2.0` 이후 다음 minor 후보인 `v0.3.0` 으로 둔다.
- 엘리베이터 dispatch loop 이란 23개 층에 대해 여러 대 엘리베이터가 동시에 움직이는 그룹 제어 시뮬레이션을 뜻한다. 현재 5개 층 단일 car 프로토타입은 이 목표의 축소본일 뿐이다.
- 엘리베이터 dispatch loop 의 다음 구현 기준은 사용자가 실시간으로 수요량을 늘리거나 줄일 수 있는 분포 제어와, step 버튼 없이 부드럽게 계속 움직이는 연속 운행 루프다.
- 엘리베이터 시뮬레이터의 기본 단위는 호출 건수가 아니라 사람 수다. 각 사람은 출발층과 목적층을 가져야 하고, 엘리베이터 한 대의 정원은 20명으로 둔다.
- 수동 조작 버튼의 기본 의미는 `상행 1명 추가`, `하행 1명 추가`처럼 승객 1명을 생성하는 것이며, 상행/하행을 같은 비중으로 다룬다.
- `v0.4.0` 은 기존 웹사이트 안의 `Work Manager` 메뉴, Jira 스타일 티켓 보드, command 패널, 비밀번호 게이트를 붙이는 운영 트랙으로 둔다.
- `v0.4.0` 은 기능 데모만으로 끝내지 않고, Work Manager 기준 테스트 코드, GitHub Actions 테스트 자동화, 커버리지 노출, PR 버전 표기 게이트까지 포함해야 한다.
- Work Manager 의 첫 실사용 흐름은 `Backlog -> Ready -> Started -> Need Review -> Finished` 로 읽히게 만들되, `v0.4.0` 에서는 사용자가 직접 드래그하는 전이는 `Backlog -> Ready` 까지만 우선 보장한다.
- `Ready -> Started` 는 worker 가 잡는 구간으로 두고, 초기 문구는 `worker agent 다른 작업 중...` 같은 대기 설명으로 둔다. 어느 worker 가 어떤 일을 하는지 보이는 가시화는 후속 버전으로 넘긴다.
- `Need Review -> Finished` 는 orchestrator/PM 확인 구간으로 두고, 초기 문구는 `PM agent 확인중...` 같은 리뷰 설명으로 둔다. orchestrator 가 무엇을 보는지 재미 요소로 풀어내는 연출은 후속 버전으로 넘긴다.
- 티켓 상세 패널에서는 대상 버전, 의존성, 우선순위를 수정할 수 있는 방향을 `v0.4.0` 에서 연다. 다만 우선순위 변경이 실제 worker 선점 순서를 자동 변경하는 실행 로직은 후속 버전으로 분리한다.
- Work Manager 상단에는 목표 버전과 현재 작업중인 버전 범위, 간단한 로드맵 요약이 함께 보여야 한다.
- 메인 포털이 길어지는 문제를 피하기 위해 스플래시 이후 첫 화면은 `Main page` 로 두고, Work Manager/엘리베이터/후속 시뮬레이터를 기능별 페이지로 분리한다. 각 기능 페이지의 뒤로가기는 Main page 복귀를 기본으로 한다.
- 첫 버전의 Work Manager 와 활동 피드는 파일 기반 저장을 유지하되, 장기적으로는 DB 기반 운영 저장소로 옮기는 로드맵을 명시한다.
- Work Manager 조회는 공개로 두고, 실행성 액션과 command 입력만 비밀번호로 잠근다.
- command 입력은 freeform 텍스트가 아니라 프리셋 액션 + 메모 조합으로 받는다.
- 오른쪽 패널에는 실제 운영감과 전시 목적을 위한 활동 로그/대화 피드를 두고, 사용자는 한 명으로 가정한다.
- 첫 버전의 활동 로그 피드는 DB 없이 파일 기반 또는 요약 seed 데이터로 시작한다.
- 각 기능 페이지의 책임, 기능 경계, 더미/실기능 분리 판단은 `docs/feature-definition.md` 를 기준 문서로 삼는다.
- 택시 시뮬레이터는 그 다음 시뮬레이션 트랙으로 두고, 본편은 `v0.5.0`, 피드백/자동학습 후속은 `v0.5.1` 으로 쪼갠다.
- Flash Game 공간은 별도 아케이드 트랙으로 두고, `v0.6.0` 에서 Ruffle 기반 플레이어 통합과 게임 카탈로그를 다룬다.
- command 창은 "Codex 직접 연결"이 아니라 gateway/worker/orchestrator 경로로 흘러가는 플랫폼 명령 브리지로 해석한다.
- 초기 공유 비밀번호 `xptmxldxptmxld` 는 frontend 하드코딩이 아니라 server-side secret 검증으로 처리한다.
- 특정 Flash 게임 파일은 합법적인 공개 배포나 사용자가 보유한 파일 기준으로만 반입한다. 권리 상태가 불명확한 SWF 를 임의 수집하거나 재배포하지 않는다.
- 안정화 작업은 필요할 때마다 추가한다.
- worker node는 오케스트레이터보다 제한적인 모델로 관여 없이 일할 수 있으므로, 티켓은 실행 지시서 수준으로 구체화한다.

## 아직 조정이 필요한 항목

- 엘리베이터 시뮬레이터의 구현 언어와 배포 단위
- 플랫폼 소개 페이지 문구와 섹션
- 사용자 서버의 OS, 접속 방식, 공개 포트
- Docker 배포용 Caddy/Let's Encrypt 자동 갱신이 실제 서버 정책과 충돌하지 않는지

## 오케스트레이터 불만과 제안

- 버전 기준을 빌드 도구 하나에 맡기는 것은 위험하다. 이 저장소는 모노레포라서 `VERSION`, `docs/releases.md`, 티켓 메타데이터를 조합하는 편이 더 안전하다.
- 공개 사이트 호스팅과 로컬 `localhost:7000` 프리뷰는 같은 목표가 아니다. 둘은 연결될 수 있지만 티켓은 분리해야 검토가 쉬워진다.
- `sample-python-service` 는 지금 목적이 약하다. `v0.1.3` 준비 슬라이스에서 필수 경로에서 제거하거나 후속 서비스 계약 후보로 대체했고, 남은 참조는 레거시 설명으로만 유지한다.
- GitHub 서버를 직접 구축하는 것은 현재 단계에서 과하다. GitHub Releases, Actions, Packages 조합으로 충분하다.
