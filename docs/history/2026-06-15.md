## 문서 인코딩 이슈 1차 진단과 chore 티켓 발부

- 사용자가 `docs/` 안의 문서가 많이 깨져 보인다고 알려 주었고, 오케스트레이터는 먼저 실제 텍스트 손상인지 인코딩/출력 경로 문제인지 구분하기로 했다.
- `docs/architecture.md` raw bytes 확인 결과 문서 바이트 자체는 정상 UTF-8 한글로 보였고, `docs/tickets/board.md`, `docs/history/2026-06-14.md` 는 UTF-8 BOM 이 있으나 `README.md`, `docs/architecture.md`, `docs/ticket-policy.md` 는 BOM 이 없는 혼재 상태임을 확인했다.
- 이 결과를 바탕으로 1차 원인을 "실제 UTF-8 텍스트 + UTF-8 BOM 유무 혼재 + Windows PowerShell 기본 인코딩 경로" 조합으로 정리했다.
- 사용자가 전체 복구를 오케스트레이터가 직접 오래 끌지 말고 `chore` 로 발부해 worker 가 처리하게 하라고 지시했다.
- 이에 따라 `TKT-044` `문서 인코딩 복구와 UTF-8 BOM 정규화`, `TKT-045` `문서 인코딩 가드레일과 체크 도구 추가` 를 backlog 에 추가했다.
- 동시에 `AGENTS.md`, `docs/ticket-policy.md`, `docs/tickets/README.md`, `docs/tickets/orchestrator.md`, `docs/tickets/worker.md`, `design/designer-role.md` 에 운영 문서는 `UTF-8 with BOM` 으로 저장하고, PowerShell/Python/Node 로 문서를 다룰 때 인코딩을 명시하라는 기준을 추가했다.

  - `POST /api/work-manager/auth` -> `Command gate unlocked`
  - `POST /api/work-manager/tickets/TKT-040/metadata` no-op payload -> `TKT-040 metadata is already up to date`

## release workflow GitHub Release 자동 생성 보강

- 사용자가 "GitHub Action 으로 Release 생성도 할 수 있지 않나" 라고 지적한 흐름을 반영해 `.github/workflows/release.yml` 을 확장했다.
- 이제 `release.yml` 은 태그와 `VERSION` 일치 여부를 검증한 뒤, 실제 태그 push 이벤트에서는 GitHub Release 를 자동 생성하거나 같은 태그의 기존 릴리스를 갱신한다.
- 구현은 `actions/github-script@v7` 기반으로 두어 별도 서드파티 릴리스 액션 의존을 늘리지 않았다.
- `workflow_dispatch` 실행은 여전히 검증/체크리스트 공유 용도고, Release 생성은 실제 태그 이벤트에서만 수행한다.
- `docs/release-automation.md` 도 이 변경에 맞춰 현재 자동화 범위와 남은 확장 지점을 다시 정리했다.
