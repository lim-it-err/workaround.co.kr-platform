## Work Manager 세부 결정 보강

- Work Manager 조회는 공개로 두고, 티켓 이동/실행과 command 입력 같은 실행성 액션만 비밀번호로 보호하기로 정했다.
- command 입력은 freeform 텍스트가 아니라 프리셋 액션 + 메모 조합으로 받는 방향으로 티켓을 보강했다.
- 오른쪽 패널에는 사용자와 AI가 지금까지 이런 식으로 일해왔다는 인상을 주는 활동 로그/대화 피드를 두기로 정했다.
- 사용자는 한 명이라고 가정하고, 이 활동 로그 피드는 첫 버전에서 DB 없이 파일 기반 JSON 또는 history 요약 seed 데이터로 시작하는 방향을 기본안으로 잡았다.
- 이 결정을 반영해 `TKT-031`, `TKT-032`, `TKT-033` 을 보강하고 새 티켓 `TKT-034` 를 `v0.4.0` backlog 로 추가했다.

## `TKT-032`, `TKT-033` Work Manager 실행 브리지/인증 게이트 구현

- `gateway` 에 `POST /api/work-manager/auth`, `POST /api/work-manager/tickets/{ticketId}/transition`, `POST /api/work-manager/commands` 를 추가했다.
- 조회 전용 `GET /api/work-manager/board` 응답도 함께 확장해 `activityFeed[]`, `commandHistory[]`, `actions` descriptor 를 내려주도록 정리했다.
- Work Manager 인증은 공유 비밀번호의 SHA-256 해시 비교 방식으로 처리하고, 성공 시 `X-Work-Manager-Token` 기반 짧은 세션 토큰을 발급하도록 구현했다.
- 실패 횟수 잠금과 TTL 은 `WORK_MANAGER_PASSWORD_SHA256`, `WORK_MANAGER_SESSION_TTL_MINUTES`, `WORK_MANAGER_MAX_FAILED_ATTEMPTS`, `WORK_MANAGER_LOCK_MINUTES` 환경 변수로 조절하도록 `gateway` 설정과 문서를 갱신했다.
- 티켓 전이는 `backlog -> started`, `started -> need_review`, `need_review -> finished` 허용 경로만 통과시키고, `started` 진입 시에는 worker/orchestrator 브리지용 플랫폼 티켓을 발행하도록 연결했다.
- command 입력은 freeform 대신 preset action + note 조합만 허용하고, 최근 실행 이력과 운영 feed 가 같은 Work Manager 패널에서 보이도록 `frontend` UI 를 갱신했다.
- fallback Work Manager 데이터와 티켓 경로도 현재 상태에 맞게 `TKT-032`, `TKT-033` 을 `need_review` 기준으로 다시 맞췄다.
- `powershell -ExecutionPolicy Bypass -File .\tools\run-frontend-build.ps1` 검증은 통과했다.
- 현재 작업 환경에는 `java`, `mvn`, wrapper 가 없어 gateway compile 검증은 아직 못 했고, 이 점을 두 티켓의 `검토 메모` 와 관련 문서에 함께 남겼다.
- 추가로 사용자가 "10초 후 메인 전환 화면과 아래 스크롤 구간까지 봐야 한다" 고 명시해, 스플래시 단독 검수는 불충분하다는 점을 디자인 감사 문서와 review 로그에 반영했다.
- 이어서 사용자가 모바일 버전도 반드시 함께 디자인해야 하고, 스크린샷 중심 검수보다 실제 페이지 탐색 방식이 더 적합하다고 정리해 주었다.
- 이에 맞춰 `design/README.md`, `design/ui-ux-rules.md`, `design/designer-role.md` 에 모바일 독립 검토 원칙과 라이브 탐색 중심 검수 방식을 추가했다.

- 후속 정리로 `docs/history/README.md` 에도 같은 잠금 규칙을 추가해 히스토리 문서까지 `수정중/작성완료` 기준을 동일하게 적용했다.

## heartbeat 범위와 버전 상한 문구 동기화

- heartbeat 자동화 이름과 프롬프트를 현재 운영 범위에 맞게 `v0.4.0 이하 + infra` 기준으로 갱신했다.
- 확인 결과 `docs/tickets/board.md` 와 실제 티켓 흐름은 이미 `v0.4.0` 티켓을 진행 중이었지만, `docs/releases.md`, `docs/version-policy.md`, `docs/roadmap.md`, `docs/steering.md` 일부 문구는 아직 `v0.3.0` 예외까지만 반영하고 있었다.
- 이 모순은 worker 가 정책 문서만 읽고도 `v0.4.0` 티켓 착수를 주저하게 만들 수 있어, 사용자 지시로 열린 선작업 범위를 `v0.4.0 이하` 까지 다시 명시했다.
- 다만 이 정리는 어디까지나 선작업 상한 동기화이며, `VERSION=0.1.0`, `v0.2.0` 미배포 상태, 각 minor 릴리스 기준선 미승인 원칙 자체는 바꾸지 않았다.
