# 로드맵

## 목적

이 문서는 제품 방향과 릴리스 방향을 분리해서 오케스트레이터와 워커가 같은 우선순위를 보게 하는 기준 문서다.

## 현재 확정된 1차 목표

`workaround.co.kr` 과 `workaround.kr` 에 첫 공개 웹사이트를 호스팅한다.

1차 목표의 의미는 아래와 같다.

- 구매한 도메인에 실제 접속 가능한 웹사이트를 올린다.
- 첫 공개 웹사이트는 플랫폼 소개 페이지를 우선한다.
- 대표 도메인(canonical domain)은 `workaround.co.kr` 로 둔다.
- `workaround.kr` 은 대표 도메인으로 리다이렉트하는 방향을 기본으로 한다.
- 첫 배포 방식은 사용자가 가진 서버 위 Docker 배포를 기본으로 한다.
- 로컬 `v0.2.0` 프리뷰와 공개 웹사이트의 역할을 구분한다.
- DNS, TLS, 배포 경로, 운영 책임을 문서화한다.
- 정적 호스팅과 클라우드 호스팅은 보조 선택지로 설명만 남기고, 첫 실행 경로로 강제하지 않는다.

관련 티켓:

- `TKT-014`
- `TKT-017`

## 현재 개발 상한

- 배포 완료 버전: `v0.1.0`
- 현재 개발 상한: `v0.5.0`
- 다음 minor 후보: `v0.3.0`
- `v0.3.0` 이후 차기 후보: `v0.4.0`
- `v0.4.0` 이후 차차기 후보: `v0.5.0`
- `v0.5.0` 이후 후속 후보: `v0.5.1`
- `v0.5.1` 이후 차차차기 후보: `v0.6.0`
- `v0.6.0` 이후 후속 후보: `v0.7.0`
- `v0.7.0` 이후 차차차기 후보: `v0.8.0`
- 진행 예외: `localhost:7000` HTTP 응답과 프런트엔드 빌드가 확인된 뒤 사용자가 범위를 열어 두었으므로, 현재는 `v0.5.0` 이하 개발 티켓까지 시작할 수 있다.
- 안정화 작업: 필요할 때 `v0.2.x` 또는 해당 시점의 patch 티켓으로 추가한다.

현재 `v0.4.0` 과 `v0.5.0` 범위의 제품 기준선은 `docs/feature-definition.md` 를 따른다. 이후 티켓 분할, 검수, 더미/실기능 경계 판단은 이 문서를 먼저 기준으로 삼는다.

## v0.3.0 준비 작업

- `TKT-011`: 엘리베이터 시뮬레이터 통합 프리뷰 연결
- `TKT-021`: 23층 다중 엘리베이터 dispatch loop
- `TKT-023`: 지하철 플랩 행선기 스타일 첫 화면 디자인 강화
- `TKT-035`: 실시간 수요 분포 반영과 step 없는 연속 이동 루프
- `TKT-049`: 엘리베이터 floor warp 완화, 가변 car 수, 승객 수 시각화 안정화

`v0.2.0` 은 아직 릴리스 게이트(`TKT-018`)가 열려 있으므로 정식 완료 버전으로 취급하지 않는다. 다만 사용자가 `0.3` 작업 시작을 직접 지시했으므로, 엘리베이터 시뮬레이터는 `v0.3.0` 선작업으로 분리해 진행할 수 있다.
`v0.3.0` 엘리베이터 라인의 현재 기준선은 "23층, 다중 엘리베이터"에서 멈추지 않는다. 여기에 사용자가 실시간으로 수요를 늘리거나 줄일 수 있는 분포 제어, 승객 수와 목적층 기반 모델, 대당 정원 20명, step 버튼 없이 계속 흘러가는 연속 이동 감각까지 포함해야 한다.
추가 안정화 슬라이스가 필요하면 `v0.3.1` patch 에서 floor warp 완화, 엘리베이터 대수 조절, car 내부 승객 수 애니메이션 같은 보강을 먼저 닫고 다음 minor 로 넘긴다.

- `TKT-032`: Work Manager 티켓 이동과 command 브리지

- `TKT-036`: Work Manager 테스트 코드, GitHub Actions, 커버리지 게이트
- `TKT-037`: PR 버전 표기와 one-version-one-feature 가드
- `TKT-039`: Work Manager `Backlog/Ready` 분리와 상세 패널
- `TKT-040`: Work Manager 메타데이터 편집과 목표 버전 헤더

- `TKT-046`: 플랩 안내 방송 문구 확장과 랜덤 로테이션

`v0.4.0` 은 `v0.3.0` 엘리베이터 시뮬레이터 다음에 들어가는 운영 트랙으로 둔다. 이 버전은 기존 웹사이트 안에 `Work Manager` 메뉴를 만들고, Jira 스타일 티켓 보드, `Backlog/Ready/Started/Need Review/Finished` 시각 흐름, `Backlog -> Ready` 드래그 이동, 티켓 상세 패널, 오른쪽 command 패널, 활동 로그 피드, 목표 버전 헤더, 간단한 로드맵 뷰, Main page 기반 기능 분리 라우팅, 다크모드, 비밀번호 게이트를 붙이는 데 집중한다. 다만 이 버전은 기능만 보이는 상태로 닫지 않고, 테스트 코드, GitHub Actions PR 테스트, 커버리지 README 노출, PR 버전 표기 가드가 갖춰져야 비로소 완료로 본다.

`Ready -> Started` 자동 전이에서 "어느 worker 가 이 일을 잡았는지"까지 보여주는 가시화와, `Need Review -> Finished` 구간의 orchestrator/PM 진행 상황을 재미 요소까지 포함해 설명하는 기능은 `v0.5.0` 후속 운영 확장으로 분리한다. 티켓 메타데이터 변경이 실제 worker 선점 순서를 즉시 바꾸는 우선순위 스케줄링도 같은 후속 범위로 둔다.

## v0.5.0 준비 작업

- `TKT-024`: 다양한 시뮬 포털 탭과 택시/엘리베이터 진입 라우팅
- `TKT-025`: 가상 지도, 랜덤/수동 요청, 택시 이동, 처리시간 중심 보상과 차량 투입 패널티를 가진 택시 시뮬레이터 코어
- `TKT-042`: Work Manager worker 할당 가시화와 우선순위 반응 실행
- `TKT-043`: Work Manager 파일 저장소에서 DB 기반 운영 저장소로 전환

`v0.5.0` 은 Work Manager 이후 이어지는 다음 시뮬레이션 트랙으로 둔다. 이 버전은 웹 포털 안에서 택시 시뮬레이터를 별도 진입점으로 열고, 시뮬레이션 코어를 독립 서비스 또는 명확한 계약으로 분리하는 데 집중한다.
다만 첫 구현안은 범위를 과도하게 키우지 않기 위해, 구역 기반 맵과 프런트 단독 시뮬레이션 코어를 기본안으로 둔다. 강화학습, RTX5070 평가, 별도 서비스 분리는 후속 슬라이스에서 연다.

## v0.6.0 준비 작업

- `TKT-050`: 블로그 허브, 공개 아카이브, 글 상세 라우팅
- `TKT-051`: 글쓰기 스튜디오, 초안/미리보기/발행 흐름
- `TKT-052`: Markdown 기반 글 저장 계약과 렌더링 파이프라인

`v0.6.0` 은 사용자가 실제로 글을 쓰고 쌓아 갈 수 있는 블로그 라인으로 둔다. 이 버전은 포털 안에 `Blog District` 또는 동등한 글 공간 진입점을 추가하고, 공개 글 목록/상세 읽기와 단일 작성자용 글쓰기 스튜디오를 여는 데 집중한다. 첫 구현은 다중 작성자 CMS 보다 단일 작성자, Markdown 우선, 초안/발행 분리, 공개 읽기 경험에 집중한다.

## 로드맵 결정 질문

로드맵 확정을 위해 사용자에게 확인할 질문은 아래와 같다.

1. 플랫폼 소개 페이지에 어떤 문구와 섹션을 둘 것인가?
2. 사용자가 가진 서버의 OS, 접속 방식, 열 수 있는 포트는 무엇인가?
3. Caddy 기준 배포에서 실제 서버 방화벽과 포트 공개 정책은 어떻게 맞출 것인가?
4. TLS 인증서는 Caddy + Let's Encrypt 자동 갱신으로 둘 수 있는가?
5. Work Manager 보드의 조회(read) 범위까지 비밀번호로 잠글지, 실행성 액션만 잠글지?
