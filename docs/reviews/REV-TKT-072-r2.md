## [블로커] 재검증 — 완전히 해소 확인

r1에서 사용했던 것과 **동일한 재현 절차 + 동일한 진단 스크립트**로 다시 측정했다(대조를 위해 r1의 수치를 나란히 적는다).

| 항목 | r1 (반려 시점) | r2 (이번 실측) |
|---|---|---|
| `.map-scroll` scrollWidth | 820 | **820** |
| `.map-scroll` clientWidth | 820 (스크롤 불가) | **299** |
| `scrollLeft = 300` 대입 후 실제 값 | `0`(무시됨) | **`300`(반영됨)** |
| `document.documentElement.scrollWidth` | 375 | **375**(불변 — 페이지 전체 가로 스크롤은 여전히 없음, 의도대로) |
| `.map-scroll`/`.map-panel` computed `min-width` | `auto`(기본값) | **`0px`** |

핵심 차이: r1에서는 `clientWidth`가 `scrollWidth`와 같아서(820=820) "스크롤할 여지 자체가 없는" 상태였는데, r2는 `clientWidth`가 실제 뷰포트에 맞게 299로 줄어들어(`min-width:0` 덕분에 flex 자식이 820px 콘텐츠 폭까지 강제로 안 늘어남) `overflow-x:auto`가 정상적으로 로컬 스크롤 영역을 만든다. `scrollLeft` 대입이 실제로 반영되는지까지 재확인했고, 시각적으로도 스크롤 후 이전엔 화면 밖에 있던 D/E/B본선/T/P 라벨이 전부 보임을 스크린샷으로 확인했다. 다크 테마에서도 동일 수치(scrollWidth 820/clientWidth 299/scrollLeft 자유 이동) 재확인 — CSS 레이아웃 수정이라 테마 무관하게 적용됨은 예상대로.

`clientWidth=299`(뷰포트 375가 아니라 299인 이유: `.map-panel`의 `padding:clamp(10px,2vw,22px)` 양쪽 + `.junction-shell`의 `gap`/여백 누적)는 PM의 r2 재개 메모에 적힌 "clientWidth 299" 수치와 정확히 일치 — PM이 실제로 측정하고 수정했음을 교차 확인.

## 완료 기준 문구 변경 건
