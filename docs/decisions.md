## D-004 확장 단위 = 모노레포 폴더, repo 신설은 예외 · 확정 (2026-08-16)

- **PO 질문**: "앞으로 홈페이지 확장할 때 해당 기능이 다 repository를 파야 하냐"
- **결정**: **아니다. 새 기능의 기본 배치는 이 모노레포 안의 폴더다.** 화면 = `frontend/src/modules/<기능>/`, 백엔드 = `services/<기능>/`, 정적 게임류 = `services/arcade/<게임>/`(TKT-028 게임 공간). 독립성은 repo 경계가 아니라 **계약**(자체 README·Dockerfile·`/health`·환경변수 문서)으로 확보한다 — `services/`에 파이썬·스프링 서비스가 이미 이 방식으로 공존한다.
- **repo 신설 예외 3조건**: ①플랫폼 밖 독자 배포/공개 ②이질 툴체인·대용량 바이너리 ③실험 단계(졸업 시 subtree 흡수).
- **편입 절차**: `git subtree add --prefix`로 원 레포 커밋 이력을 보존하며 흡수 → 원 레포는 아카이브(화석 main 방지).
- **가드**: 티켓에 `scope`(수정 허용 파일 화이트리스트) 필드를 도입해 에이전트가 자기 폴더 밖을 건드리는 사고를 규칙으로 막는다 (화이트채플 works 체계에서 이식). 서브모듈은 채택하지 않는다 — 이 조직의 브랜치 화석화·워킹트리 공유 사고 이력에 실패 모드를 추가하기 때문.

## D-009 공개 사이트의 LLM 기능은 반드시 gateway 경유 · 확정 (PO 2026-08-18 J4)

- **배경**: PO 질문 — "블로그에 Ollama 쿼리를 두면 docker 로 가둬도 가능할까? 호스팅 서버와 Ollama 서버가 다른데 중간에 gateway 까지 있어야 하나?"
- **제안**: 가능하되, **공개 트래픽이 RTX5070 Ollama 에 직접 닿는 경로는 만들지 않는다.** 경로는 항상 `Caddy(TLS) → gateway → 큐/정책 → RTX5070 Ollama`. docker 격리는 서버 탈취 반경을 줄일 뿐이고, 실제 위험(GPU 자원 고갈·남용·프롬프트 인젝션·게이밍 중 다운)은 **호출 경로 통제**로 막는다:
  1. gateway 에서 rate limit + 요청 큐(동시 1~2) + 입력 길이 상한
  2. 프롬프트는 서버측 고정 템플릿(사용자 입력은 변수로만) — 시스템 프롬프트 노출·탈취 방지
  3. RTX5070 인바운드는 호스팅 서버 IP 만 허용, Ollama 는 공인망에 절대 미노출
  4. Ollama 다운 시 degraded 응답(기존 ollama-policy 의 graceful degradation 그대로)
- **근거**: 기존 아키텍처 원칙("서비스는 Ollama 직접 의존 금지, worker/gateway 정책 경로")의 공개망 확장일 뿐 — 새 구조가 아니다. gateway 는 이미 이 목적으로 존재한다.
- **상태**: 확정. 블로그 질의 위젯 티켓은 TKT-068(RTX5070 Ollama 구동)·TKT-004(오프로드 계약) 뒤에 발행.
