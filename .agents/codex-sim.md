## 레인 공통 규칙

- **스펙이 없는 티켓은 집지 않는다** — `[SIM]` 티켓은 반드시 design/ 스펙을 참조한다. 스펙과 충돌하면 구현을 멈추고 질문 섹션에 기록.
- 도메인 계약 불변: 사람 단위 모델, 연속 위치·보간(워프 금지), 상·하행 대칭.
- 완료 게이트: `cd frontend && npm run build` + 다크/라이트 + 모바일 375px 오버플로 0 + **방치 30초 관찰 시 화면에 시뮬레이션 변화가 보인다**(스크린 기록 요약).

## 상주 루틴 (깨어날 때마다, 매번 이 순서)

1. 이 문서와 보드를 디스크에서 새로 읽는다 — 이전 실행 기억 사용 금지.
2. **직속 지시함 `../inbox/codex-1.md (newProject 루트)` 를 먼저 본다** — 티켓 ID 지정 시 그것이 최우선 (규칙은 inbox/README.md). 
3. 보드에서 `[SIM]` 태그 중: 내 started 이어서 → 반려 우선 → 없으면 ready 최우선 집고 started 전환+보드 갱신 → 집을 게 없으면 종료(빈 실행 정상).
4. 티켓·스펙 전부 읽고 구현. 스펙에 없는 기능 추가 금지.
5. 게이트 실행·출력 기록 → need_review + 보드 + history 3줄.
6. 막히면 질문 섹션 + blocked. **git 커밋 금지.**

## UX·가시성 1순위 + 반박 의무 (PO 2026-09-14 — 전 에이전트 공통)

- **구현·검증의 1순위는 사용성과 가시성이다.** 기능이 돌아가도 화면이 지저분하면 완료가 아니다. need_review 전환 전에 375px·1440px 실렌더를 스스로 보고, 원칙(`design/tone-principles-2026-09-09.md`)과 목업 대비 어긋난 점을 티켓에 적는다.
- **반박하라.** 티켓·스펙·목업이 사용성을 해친다고 판단되면 그대로 구현하지 말고 티켓 `## 질문/에스컬레이션` 에 `[반박]` 태그로 이유+대안을 적는다. 모호하면 `[구체화 질문]`. 둘 다 blocked 가 아니라 **진행하면서** 남기되, 판단이 갈리는 지점은 PM 답을 기다린다.
- **소통은 파일로.** 티켓의 질문 섹션·history 가 채널이다. "그냥 했다"는 금지, "이렇게 했고 이 부분은 확신이 없다"가 정답.
