# UI/UX 규칙

## 제품 성격

- 이 사이트는 일반적인 SaaS 랜딩 페이지보다 "운영 포털" 에 가깝다.
- 서울 지하철, 관제실, 역무실의 분위기는 유지하되, 사용성이 콘셉트를 이겨야 한다.
- 서울지하철 콘셉트는 배경 이미지가 아니라, 노선/환승/출구/플랫폼처럼 정보 구조 자체에 반영한다.
- 한 화면에 정보가 많더라도 읽는 순서와 우선순위는 명확해야 한다.
- 모바일 버전은 축소판이 아니라 독립 설계 대상으로 본다.
- 포털이 길어지면 한 화면에 모든 것을 늘어놓지 말고 Main page 에서 기능별 페이지로 분리한다.
- 라이트/다크 모드는 둘 다 1급 화면으로 취급한다. 다크모드는 라이트모드의 반전판이 아니라 같은 위계와 읽기성을 유지하는 짝 설계여야 한다.

## 시각 원칙

- 분위기와 기능을 분리한다.
  - 분위기: 지하철, 플랩, 관제실, 금속성 표면
  - 기능: 상태 확인, 서비스 이동, 명령, 리뷰
- 강조 색은 "지금 어떤 노선/기능에 있는가"를 알리는 용도로 우선 사용한다.
- 과한 장식은 첫 화면 한정으로 쓰고, 메인 운영 화면은 더 건조하고 빠르게 읽혀야 한다.
- 검은 대면적 영역은 의미 없는 여백으로 남기지 않는다.
- 강한 콘트라스트는 유지하되, 텍스트 밀도는 줄이고 계층은 더 선명하게 나눈다.

## 정보 구조 원칙

- 사용자가 가장 먼저 봐야 하는 것은 "지금 무엇을 할 수 있는지" 다.
- 스플래시는 브랜드와 세계관 소개 역할까지만 맡고, 메인 화면에서는 실사용 정보를 우선한다.
- 메인 화면이 라우터 역할을 맡는 경우, 메인에서는 실제 기능을 수행하지 않고 각 기능 페이지로 갈라지는 선택과 이동만 제공한다.
- 메인 화면은 지하철 중앙 환승 홀처럼, 기능 페이지는 개별 승강장처럼 읽혀야 한다.
- 한 섹션에 너무 많은 역할을 섞지 않는다.
  - 서비스 진입
  - 시뮬레이터 조작
  - 런타임 상태
  - Work Manager
  - 최근 티켓
- Work Manager 는 중요하지만 현재 메인 페이지에서 다른 기능과 경쟁 중이므로, 독립된 시각 리듬을 가져야 한다.
- 메인 페이지는 "환승 홀", 기능 페이지는 "승강장"처럼 역할을 분리한다.
- 출구 번호, 환승 가능 노선, 현재 위치 같은 wayfinding 정보는 선택 UI에서 적극적으로 드러낸다.

## 반응형 원칙

- 모바일에서는 "축소" 가 아니라 "재배치" 를 기본으로 본다.
- 큰 데스크톱 레이아웃을 세로로 접기만 하지 않는다.
- 스플래시에서 의미 없는 검은 여백이 화면 대부분을 차지하면 안 된다.
- 모바일에서도 자동 전환 뒤 핵심 작업으로 자연스럽게 이어져야 한다.
- 모바일에서도 "짧은 환승 허브 -> 개별 기능 진입" 구조가 먼저 읽혀야 한다.
- 모바일에서 우선순위는 아래 순서를 따른다.
  1. 현재 상태
  2. 주요 진입
  3. 핵심 시뮬레이터 또는 Work Manager
  4. 보조 상태 패널

## 검증 원칙

- 각 변경은 데스크톱과 모바일을 모두 확인해야 한다.
- 각 변경은 최소 아래 장면을 확인해야 한다.
  1. 첫 진입 스플래시
  2. 10초 후 메인 화면 상단
  3. 아래 스크롤 구간
  4. Work Manager 또는 핵심 시뮬레이터 진입 구간
- 디자인 평가는 캡처 한 장보다 실제 탐색 흐름을 더 우선한다.

## 인터랙션 원칙

- preview 전용 액션과 실제 실행 액션은 시각적으로 더 명확히 구분한다.
- 상태 badge 는 예쁘기보다 빠르게 읽혀야 한다.
- CTA 문구는 "무엇이 열리고 어떤 결과가 나는지" 를 직접 말해야 한다.
- 메인 페이지 CTA 는 상세 기능 실행이 아니라 기능 페이지 진입을 명확히 안내해야 한다.
- 현재 위치, 이동 가능 경로, 돌아가기 동선은 실제 역 안내처럼 반복적으로 확인 가능해야 한다.
- feed, ticket, runtime 상태는 모두 같은 문장 톤으로 정리한다.
- 드래그 가능한 상태와 시스템 전용 상태를 섞어 보이게 하지 않는다. 예를 들어 `Backlog -> Ready` 는 사용자가 끌 수 있지만, `Ready -> Started` 는 worker 소유 전이로 읽혀야 한다.
- 상세 패널은 단순 보기 전용이 아니라 "무엇을 바꿀 수 있고, 무엇은 아직 사람이 결정해야 하는지"를 구분해 보여줘야 한다.

## 오케스트레이터 handoff 규칙

- UI/UX 구현 티켓은 반드시 관련 디자인 문서를 링크한다.
- acceptance criteria 에 아래 항목을 포함한다.
  - 데스크톱/모바일 레이아웃
  - 정보 우선순위
  - 상태 읽기성
  - preview/real action 구분
  - 접근성 또는 대비 확인 포인트
