# UX 카피 감사 — 화면이 난해한 이유 (2026-08-16)

PO 피드백: **"화면에 너무 뭐가 많고 목표가 안 보여 난해해. 특히 메뉴를 설명하는 문구가 너무 많아."**
첫 화면(스플래시) 제외 전 페이지를 전수 감사한 결과와, 즉시 적용한 조치(TKT-081)의 기준 문서.

## 1. 진단 — 왜 난해했나

소스 전수 조사(App.vue 템플릿) 결과, 문제는 레이아웃보다 **글**이었다.

1. **화면이 자기 자신을 해설한다.** 환승 홀에만 "이 화면은 요약만 하는 구간입니다" 류 메타 문단이 **4개** 있었다 (hero 94자 + 캡션 37자 + 리뷰 섹션 55자 + 하단 설교 70자). 사용자는 "무엇을 할 수 있나"를 찾는데 화면은 "내가 무엇인지"를 반복해서 말했다.
2. **설계 의도·버전 서사가 사용자 화면에 노출.** "`v0.5.0` 은 누가 어떤 티켓을 집었는지…", "이번 버전의 핵심은…" — 이것은 `docs/history/` 의 내용이지 UI 카피가 아니다.
3. **내부 용어 유출.** 환승 홀·Sim Hub 카드에 `TKT-024` 같은 티켓 번호 칩, "Orchestrator Review" 섹션이 사용자 대면으로 노출.
4. **같은 말을 세 겹으로.** 역명판(S1)이 페이지 정체·상태·요약을 이미 말하는데, 그 아래 리드 문단(평균 105자)이 같은 내용을 다시 서술 — live 7페이지 전부.
5. **결과 수치**: 설명성 문단만 페이지당 1~5개, 환승 홀 한 화면에 설명 텍스트 ~260자 + 내부 용어 칩 십수 개.

## 2. 카피 원칙 (이후 모든 화면 작업의 수용 기준)

1. **화면은 자기 설명을 하지 않는다.** "이 화면은 ~입니다" 금지. 화면의 정체는 역명판과 구조가 말한다.
2. **메뉴/카드 = 이름 + 상태 + 한 줄 요약(≤25자).** 설계 의도·비유·버전 서사 금지.
3. **내부 용어(TKT-###, orchestrator, slice) 사용자 화면 금지.** 필요하면 `/test` 가상 레일로.
4. **버전은 데이터로만** (상태 칩 안의 `v0.5.0 live` 는 허용, 문장 서술은 금지).
5. **한 정보는 한 곳에서만.** 역명판 summary 에 있는 내용을 본문에서 반복하지 않는다.
6. **리드 문단은 페이지당 최대 1개, ≤40자.** 그 이상은 문서(docs/) 소관.

## 3. 적용 내역 (TKT-081, live 페이지 한정)

| 위치 | 조치 |
|---|---|
| 환승 홀 hero 해설 94자 | 삭제 (h3 한 줄만 유지) |
| 환승 홀 "노선 입구" 캡션 · 하단 설교 · rail-caption | 삭제 |
| 환승 홀 "Orchestrator Review" 섹션 전체 | 삭제 (스펙 §4 도 S2 에서 제거 지시 — 선행 적용) |
| 환승 홀 "모바일 동선" 패널 (디자인 서사) | 삭제 |
| 환승 홀·Sim Hub 카드의 TKT-### 칩 | 삭제 (proto/test 레일은 유지) |
| live 7페이지 리드 문단 (평균 105자) | 삭제 — 역명판 summary 가 대체 |
| 블로그 상태 설명 3건 | "작성 중 · Studio 전용" / "공개 목록에 노출" / "보관 · 삭제 아님" 로 압축 |
| 택시 점수 설명 3건 | "빠른 배차 = 보상" / "차량 추가 = 패널티" / "보상 − 패널티 = 순점수" |
| Studio 새 초안 버튼 설명 | "편집 중인 글은 유지됩니다." |

총 **~2.9천 자 제거**. 기능·데이터·상태 표시는 전부 유지 (통계, 카드, CTA 무변경).

## 4. 남은 것 (후속 슬라이스 연계)

- 환승 홀의 근본 재구성(카드 그리드 → 노선도)은 **S2/TKT-072** — 이번 조치는 그 전까지의 감량.
- 페이지 본문 안쪽의 패널 단위 서술(elevator 조작 패널 설명 등)은 **S4/TKT-074** 에서 §2 원칙 적용.
- 이 문서의 §2 원칙을 S2~S6 티켓의 수용 기준에 추가했다.
